## 四、一次判断失误的记录（值得留）

排查发布根目录时，我先测了 `/docs/交付文档/01-需求说明书.md`、`/README.md`、`/tools/ocr.py`，四个全部返回 **200**，一度以为「Cloudflare 把整个仓库根都发布出去了，等于把工程记录也暴露在网上」。

实际去读返回内容才发现：**这四个 200 返回的都是 7,216 B 的首页 HTML**——站点开了 SPA 兜底，任何未知路径都回首页。

教训很直接：**只看状态码不看响应体，会把兜底当成命中。** 判断「某路径是否真的被发布」必须比对响应体的内容或 Content-Type，不能只信 200。

已确认的真实情况：部署根是 `source/ai-drama-studio/web-app`（`/css/style.css` 能返回真实 CSS 是证据），仓库根的 `docs/`、`tools/`、`README.md` **没有**被发布，不存在信息暴露问题。

## 五、历史文档为什么没有改

`docs/交付文档/06-技术方案V2.md`、`07-技术方案V2第二块.md` 里多处写着「在线地址 `https://jiang-ling1023.gitee.io/ai-drama-studio/`」，`docs/交付文档/README.md` 引用时也照抄了。

**这些是历史交付物的原件，不改。** 理由：

1. 它们在写下的当时是正确的——那份技术方案就是基于 Gitee Pages 论证的（连「免费版不自动重建」这个坑都写进去了）。
2. 回填改写会让「文档与代码版本对账」失效。我们刚建立的结论是「文档停在 v2、代码到 v4」，如果现在去改旧文档的字，这份对账本身就不可信了。
3. 变更另有归口——就是本文件。谁想看当前地址，看 README；谁想追溯历史决策，看 06/07 原件。

## 六、还需要用户确认的一件事

Cloudflare Pages 是否绑定了 GitHub 仓库的 Git 集成，**从外部探测不出来**：

- 若已绑定 → 每次 push 自动发布，「改了线上没变」这类问题不再存在
- 若未绑定 → 需手动上传，push 之后线上仍是旧版本

这一点已写进 `DEPLOY.md` 第二节，请在 Cloudflare 面板核对。这决定了以后「提交完是不是就完事了」。
