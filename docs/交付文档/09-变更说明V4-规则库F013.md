## 二、新增根字段：`检查前置确认`

| 项 | 内容 |
|---|---|
| 类型 | `{ 文字: boolean, 图: boolean, 视频: boolean }` |
| 默认 | 三者全 `false` |
| 定位 | 「检查前置三级确认唯一真值」（`schema.js:79` 原注释） |
| 语义来源 | `RULE-03 检查前置`：「先修文字 → 再修图 → 再进视频；不得跳级生成」 |

**三布尔各自的判定口径（`RULE-03` 正文逐字）：**

| 布尔 | 通过条件 | 对应模块 |
|---|---|---|
| `文字` | 剧本非空且场次 > 0 | F-001 |
| `图` | 图片 / 关键帧成功产物 > 0 | F-006 |
| `视频` | 片段清单 > 0 | F-011 |

**⚠️ 一处必须说清的实现事实（避免误判）：**

`RULE-03` 写「生成视频前三级未全确认即阻塞」，但代码里的实际强度是**分级的**（`director.js:311-318`）：

```js
const 含视频 = /视频|全片|F-011/.test(范围文本);
const 严重度 = 含视频 && !前置.视频 ? FINDING_SEVERITY.阻塞 : FINDING_SEVERITY.提示;
```

即：

- 复核范围**含视频生成**且 `视频` 未确认 → 判 **阻塞**
- 其余情况（范围不含视频，或视频已确认）→ 只判 **提示**

而且 `p011-video.js` 里**没有**对该三布尔做硬拦截——它照常可以「生成片段清单」。原因是本案 F-011 只做结构化编排、不产出 mp4/webm，本来就不存在「最贵的一步」。所以这道闸的落地形态是**复核报告里的阻塞项**，不是按钮禁用。

这一点如果按文档字面理解去验收，会得出「未实现阻塞」的错误结论。**实际情况是：闸门存在，但装在复核报告上，不在视频页按钮上。**

## 三、`rulesLibrary` 结构

```js
rulesLibrary: {
  内置规则: BUILTIN_RULES,   // 18 条，只读，随包预置
  固定引用: []               // 用户「固定到项目」的引用，{ 固定ID, 规则ID, 固定时间 }
}
```

**关键设计约束（CR-05-05）：**

> 「是否固定到项目」**不存第二份布尔**，而是由 `固定引用` 派生。

```js
const 固定 = new Set(固定引用.map(x => x.规则ID));
return 内置规则.map(r => ({ ...r, 是否固定到项目: 固定.has(r.规则ID), 来源: RULES_SOURCE }));
```

这是为了避免「布尔标记与实际引用不同步」这类经典脏数据。**任何新代码都不得往规则条目上写 `是否固定` 字段。**

**内置区只读**：`BUILTIN_RULES` 随包加载，界面不提供改写入口。用户只能「固定/取消固定」，不能改规则正文。

## 七、F-013 模块功能规格

唯一读写入口 `js/core/rules-library.js`。对外 9 个函数：

| 函数 | 作用 | 关键规则 |
|---|---|---|
| `getRules(project)` | 取全部规则，附加 `是否固定到项目` 与 `来源` | 派生固定态，不存第二份布尔；旧工程无 `rulesLibrary` 时回落打包副本，**不因缺字段报错** |
| `queryRules(project, {阶段, 类型, 关键词})` | 双维筛选 + 关键词 | 阶段与类型**可叠加**；关键词命中「标题 / 摘要 / 正文 / 标签」任一即算 |
| `countByStage(project)` | 五阶段计数 | 固定返回 5 个键：剧本 / 分镜 / 画面资产 / 视频 / 审阅 |
| `isFixed(project, ruleId)` | 是否已固定 | 查 `固定引用` |
| `toggleFix(project, ruleId)` | 固定一条 | **幂等**：重复固定不产生第二条引用，返回 `{ok:false, reason:'已固定'}`；规则不存在返回 `规则不存在` |
| `unfixRule(project, ruleId)` | 取消固定 | 未固定返回 `{ok:false, reason:'未固定'}` |
| `getTemplates(project)` | 取 5 套模板 | 空/缺则回落打包副本 |
| `getCompositions(project)` | 取 24 个预设 | 同上 |
| `recommendCompositions(project, sceneText, emotionTag, topN=3)` | 构图推荐 | 见下 |

**推荐算法（`recommendCompositions`）**：

```
文本 = sceneText + ' ' + emotionTag
每条预设：命中数 = (适用场景 按 / 、 拆分) ∩ 文本 的词条个数
按命中数降序，命中数相同保持原组别顺序
取前 topN（默认 3）
推荐理由 = "适用场景命中 N"
```

这是纯字符串匹配的轻量推荐，不是模型推荐——**零网络请求**，符合「零密钥可体验」的整体约束。

**固定引用的结构**：`{ 固定ID: uid('fx'), 规则ID, 固定时间 }`。注意没有「是否固定」布尔，也没有快照正文——规则正文永远从内置区读，所以内置规则升级后，已固定项自动跟着更新，不会出现「固定了旧版本」。

## 八、迁移规则（`schema.js:162-178`）

```js
// v3→v4：补 3 集合与检查前置确认（三布尔默认 false）；已有 rulesLibrary / 固定引用 一律保留，只补缺失内置区
if (raw && raw.schemaVersion === 3) {
  // ① 三布尔：对象不存在则整体补；存在则逐键补 boolean
  if (!raw.检查前置确认 || typeof raw.检查前置确认 !== 'object')
      raw.检查前置确认 = { 文字: false, 图: false, 视频: false };
  else for (const k of ['文字', '图', '视频'])
      if (typeof raw.检查前置确认[k] !== 'boolean') raw.检查前置确认[k] = false;
  // ② rulesLibrary：已有固定引用一律保留
  if (!raw.rulesLibrary || typeof !== 'object') raw.rulesLibrary = { 内置规则: [], 固定引用: [] };
  if (!Array.isArray(内置规则) || !内置规则.length) 内置规则 = BUILTIN_RULES 深拷贝;
  if (!Array.isArray(固定引用)) 固定引用 = [];
  // ③ 模板与预设：只在缺失或为空时补
  if (!Array.isArray(ruleTemplates) || !ruleTemplates.length) ruleTemplates = BUILTIN_TEMPLATES;
  if (!Array.isArray(compositionPresets) || !compositionPresets.length) compositionPresets = BUILTIN_COMPOSITIONS;
  raw.schemaVersion = 4;
}
```

**四条设计意图：**

1. **`固定引用` 优先于 `内置规则`**——注释原话「已有 rulesLibrary / 固定引用 一律保留，只补缺失内置区」。用户的固定选择绝不因迁移丢失。
2. **逐键校验 boolean**，而不是整体判断对象存在。防止 `{文字: true}` 这种残缺对象让 `视频` 变成 `undefined`（会造成 R-02 误判）。
3. **空数组也视为「需要补」**（`!length`），因为内置区空了等于功能没用。
4. **深拷贝**：`标签` 和 `占位符` 数组都做了 `[...]` 展开，避免多个工程共享同一份数组引用（这是一个很隐蔽的串数据 bug 来源）。

## 十、已知缺口（诚实记录）

1. **v4 完全没有原始文档**。01–07 里「规则库」与「F-013」提及次数均为 0；代码注释也没有引用任何「V4 §x」。所以本文是**唯一规格**，也正因如此它必须与代码逐条对齐——它承担的是原始契约本该承担的角色。
2. **18 条规则的 `正文` 未在本文完整抄录**（每条正文 200–400 字，合计约 5000 字）。本文只给结构与摘要，正文属产品内容、应在 `js/demo/rules-library.js` 或页面内维护，抄进规格文档反而会制造第二份真源。
3. **规则「类型」的枚举未在 `constants.js` 中固化**：代码里是字符串字面量（提示词 / 方法论 / 判定口径 / 模板引用），没有对应 `export const`。这违反了项目「枚举单一来源」的惯例，属可改进点。
4. **`RULE-10` 明确说 24 预设只并入「02 构图的第 4 子项」**，但 `EL_FRAMEWORK['02-构图'].构图法则` 本身仍是 7 个值，24 预设是运行期并集。这个「静态 7 值 / 运行期 31 值」的双态在代码里没有注释说明，容易被后人误改。
5. **未覆盖 `pages/p013-rules.js`（12 KB）的交互细节**：页面级筛选器联动、固定按钮文案反馈、空状态引导等未逐条展开。
